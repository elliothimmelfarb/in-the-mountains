# Development Archive — organizing the docs into a shipped, chronological story (2026-06-07)

**Goal:** the project had accumulated a large, scattered body of documentation — 8 standalone HTML
reports, ~18 dated progress folders, 16 tracked issues — all under `docs/`, which **is not served at
deploy**. Pull it together into a single chronological "how this was built" archive, integrate it with
the in-world Field Manual, make it ship with the app (transparent + visible), and codify the practice so
every future report lands there automatically.

## What was built

- **`public/manual/archive/index.html`** — the Development Archive: a chronological, narrative timeline
  of 21 development chapters (Act I walkable valley · Act II deep systems · Act III cinema · the method
  itself). Each chapter card states the player-facing problem, the *shape* of the work (the craft), the
  **verbatim before→after numbers**, a hero thumbnail, and a link to the full report where one exists.
  Visually native to the manual (reuses `../style.css`, extends with a local archive layer).
- **`public/manual/archive/reports/<slug>/`** — the 8 polished HTML reports + the visual-overhaul art
  bible, **published forward** (copied, not moved) with only the images each one references, and
  cross-links rewritten so they resolve in the new served location. The raw record stays in
  `docs/progress/` and `docs/issues/`.
- **`public/manual/archive/assets/<slug>`** — one curated hero thumbnail per chapter (19 copied from
  the progress corpus; 2 generated by screenshotting the published report pages themselves).
- **Discoverability:** linked from the manual nav (`index.html`, `tutorial.html`), and a new
  **"How It Was Built"** button on the title-screen menu (`components/screens/MenuScreen.tsx`).
- **Doctrine:** `CLAUDE.md` §4 (Delivery) + §6 (done-gate) now require every HTML report/explainer to be
  published into `public/manual/archive/` and added as a chapter — a report that ships only in `docs/`
  is invisible to players.

## How it was made (the reproduction technique — load-bearing)

1. **Recon** the doc landscape: `find docs -name '*.html'`, per-folder `du -sh`, and a precise
   dependency extract per report (`grep -oE "(src|href)=..."` filtering `data:`/`http:`) so only the
   images each report actually uses get published — 24 MB, not the full 79 MB of `docs/progress`.
2. **Survey fan-out** (a background `Workflow`, 21 Sonnet readers, one per chapter): each read its
   report(s) + the issue ledger and returned a strict schema — punchy title, problem, approach, **verbatim
   numbers**, hero image, pull-quote, `confidence`, `evidence` (`file:line`). All 21 returned with
   confidence ≥ 0.88. This kept the orchestrator's context clean for synthesis (the hard part).
3. **Synthesize** the index by hand from the structured beats (one mind for coherence), styling
   before→after metrics as red→green pills.
4. **Verify in the real served layout:** `python3 -m http.server --directory public` (mirrors the deploy
   path `/manual/...`), then a curl sweep asserting **every** `img src` and report `href` returns
   `200` (all 30 did), plus Playwright renders of the hero, a chapter card, and the closing meta-chapter
   — self-critiqued over two rounds.
5. **Standing checks:** `tsc`, `lint`, `build`, `smoke` — all green (the only code touched was the menu
   link).

## Honest residue

- The archive is a **curated** subset: the polished HTML reports are published; the raw `.md`/`.txt`
  baselines and per-tick traces stay in `docs/progress/` as the engineering record (linked, not copied).
- Two chapters (COIN, June-6 atmospherics) had no single after-screenshot in their folders; their heroes
  are, respectively, the COIN HUD shot and a render of the report page itself.
- Archive weight is ~24 MB of images, dominated by the world-scale report's 3.3 MB inline-SVG `report.html`.
  Acceptable for a game repo; a future pass could thumbnail-compress the hero assets if it matters.
